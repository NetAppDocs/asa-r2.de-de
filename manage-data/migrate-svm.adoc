= Migrieren einer Speicher-VM von einem ASA -Cluster zu einem ASA r2-Cluster
:allow-uri-read: 
:icons: font
:imagesdir: ../media/


[role="lead"]
Ab ONTAP 9.18.1 ist es möglich, eine Storage Virtual Machine (VM) unterbrechungsfrei von einem beliebigen Standard ASA Cluster zu einem beliebigen ASA r2 Cluster zu migrieren, um die vereinfachte, optimierte Architektur von ASA r2 Systemen für reine SAN-Umgebungen zu übernehmen.


NOTE: Eine Storage-VM kann nicht von einer ASA MetroCluster auf einen ASA r2 Cluster migriert werden. ASA r2 Systeme unterstützen MetroCluster Konfigurationen nicht.

ASA r2 Systeme unterstützen die QuickAssist Technology (QAT). ASA Systeme unterstützen QAT nicht. Ab ONTAP 9.20.1 verringert ONTAP die hohe Leselatenz und CPU-Auslastung, die nach der Migration einer Storage Virtual Machine (VM) von einem ASA System (ohne QAT) auf ein ASA r2 System (mit QAT) auftreten können.

Die Migration von Storage-VMs zwischen ASA und ASA r2-Speichersystemen wird wie folgt unterstützt:

[cols="2"]
|===
| Von jedem der folgenden ASA Systeme: | Für jedes der folgenden ASA r2-Systeme: 


 a| 
* ASA C800
* ASA C400
* ASA C250
* ASA A900
* ASA A800
* ASA A400
* ASA A250
* ASA A150
* ASA AFF A800
* ASA AFF A700
* ASA AFF A400
* ASA AFF A250
* ASA AFF A220

 a| 
* ASA A1K
* ASA C30
* ASA A90
* ASA A70
* ASA A50
* ASA A30
* ASA A20


|===
Die aktuellste Liste der ASA und ASA r2-Systeme finden Sie hier:link:https://hwu.netapp.com/["NetApp Hardware Universe"^] Die  ASA r2-Systeme werden im NetApp Hardware Universe als „ASA A-Serie/C-Serie (Neu)“ aufgeführt.

Sie können eine Storage VM nur von einem ASA-Cluster auf einen ASA r2 Cluster migrieren. Die Migration von jedem anderen Typ von ONTAP System auf ein ASA r2 System wird nicht unterstützt.

.Bevor Sie beginnen
Alle Knoten im ASA r2-Cluster und im ASA Cluster müssen mit ONTAP 9.18.1 oder höher laufen.  Die ONTAP 9.18.1 Patch-Versionen auf den Clusterknoten können variieren.



[[step-1-verify-the-status-of-the-asa-storage-vm]]
== Schritt 1: Überprüfen Sie den Status der ASA -Speicher-VM

Bevor Sie eine Storage-VM von einem ASA -System migrieren, dürfen keine NVMe-Namespaces oder vVols vorhanden sein und jedes Volume in der Storage-VM sollte nur eine LUN enthalten.  Die Migration von NVMe-Namespaces und vVols wird nicht unterstützt.  Die Architektur von ASA r2-Systemen erfordert, dass Volumes jeweils eine einzelne LUN enthalten.

.Schritte
. Überprüfen Sie, ob in der Speicher-VM keine NVMe-Namespaces vorhanden sind:
+
[source, cli]
----
vserver nvme namespace show -vserver <storage_VM>
----
+
Wenn Einträge angezeigt werden, müssen die NVMe-Objekte vorhanden sein.link:https://docs.netapp.com/us-en/ontap/nvme/convert-namespace-to-lun-task.html["konvertiert"^] zu LUNs oder entfernt.  Siehe die `vserver nvme namespace delete` und die `vserver nvme subsystem delete` Befehle in derlink:https://docs.netapp.com/us-en/ontap/concepts/manual-pages.html["ONTAP-Befehlsreferenz"^] für weitere Informationen.

. Überprüfen Sie, ob in der Speicher-VM keine vVols vorhanden sind:
+
[source, cli]
----
lun show -vserver <storage_VM> -class protocol-endpoint,vvol
----
+
Falls vVols vorhanden sind, sollten diese auf eine andere Storage-VM kopiert und anschließend von der zu migrierenden Storage-VM gelöscht werden.  Siehe die `lun copy` Und `lun delete` Befehle in derlink:https://docs.netapp.com/us-en/ontap/concepts/manual-pages.html["ONTAP-Befehlsreferenz"^] für weitere Informationen.

. Überprüfen Sie, ob jedes Volume in der Speicher-VM eine einzelne LUN enthält:
+
[source, cli]
----
lun show -vserver <storage_VM>
----
+
Wenn ein Volume mehr als eine LUN enthält, verwenden Sie die `volume create` Und `lun move` Befehle zum Erstellen eines 1:1-Volume-zu-LUN-Verhältnisses. Siehe dielink:https://docs.netapp.com/us-en/ontap/concepts/manual-pages.html["ONTAP-Befehlsreferenz"^] für weitere Informationen.



.Was kommt als Nächstes?
Sie sind nun bereit, eine Cluster-Peer-Beziehung zwischen Ihren ASA und ASA r2-Clustern herzustellen.



[[step-2-create-a-cluster-peer-relationship-between-your-asa-and-asa-r2-clusters]]
== Schritt 2: Erstellen Sie eine Cluster-Peer-Beziehung zwischen Ihren ASA und ASA r2-Clustern.

Bevor Sie eine Storage-VM von einem ASA Cluster zu einem ASA r2-Cluster migrieren können, müssen Sie eine Peer-Beziehung erstellen.  Eine Peer-Beziehung definiert Netzwerkverbindungen, die es ONTAP Clustern und Speicher-VMs ermöglichen, Daten sicher auszutauschen.

.Über diese Aufgabe
Der ASA Cluster ist der Quell-Cluster, von dem die Storage VM migriert wird, und der ASA r2 Cluster ist der Ziel-Cluster, zu dem die Storage VM migriert wird.

.Bevor Sie beginnen
Sie müssen auf jedem Knoten in den Clustern, die miteinander verbunden sind, Intercluster-LIFs mit einer der folgenden Methoden erstellt haben.

* link:https://docs.netapp.com/us-en/ontap/peering/configure-intercluster-lifs-share-data-ports-task.html["Konfigurieren Sie Intercluster-LIFs auf gemeinsam genutzten Datenports"^]
* link:https://docs.netapp.com/us-en/ontap/peering/configure-intercluster-lifs-use-dedicated-ports-task.html["Intercluster-LIFs auf dedizierten Datenports konfigurieren"^]
* link:https://docs.netapp.com/us-en/ontap/peering/configure-intercluster-lifs-use-ports-own-networks-task.html["Intercluster-LIFs in benutzerdefinierten IPspaces konfigurieren"^]


.Schritte
. Auf dem Ziel-Cluster wird eine Peer-Beziehung mit dem Quell-Cluster erstellt und eine Passphrase generiert:
+
[source, cli]
----
cluster peer create -peer-addrs <source_cluster_LIF_IPs> -generate-passphrase
----
+
Das folgende Beispiel erstellt eine Cluster-Peer-Beziehung zwischen Cluster 1 und Cluster 2 und generiert eine systemgenerierte Passphrase:

+
[listing]
----
cluster1::> cluster peer create -peer-addrs 10.98.191.193 -generate-passphrase
Passphrase: UCa+6lRVICXeL/gq1WrK7ShR
            Peer Cluster Name: cluster2
            Initial Allowed Vserver Peers: -
            Expiration Time: 6/7/2017 09:16:10 +5:30
            Intercluster LIF IP: 10.140.106.185
Warning: make a note of the passphrase - it cannot be displayed again.

----
. Kopieren Sie die generierte Passphrase.
. Auf dem Quell-Cluster erstellen Sie eine Peer-Beziehung mit dem Ziel-Cluster:
+
[source, cli]
----
cluster peer create -peer-addrs <destination_cluster_LIF_IPs>
----
. Die auf dem Ziel-Cluster generierte Passphrase eingeben.
. Überprüfen Sie, ob die Cluster-Peer-Beziehung erstellt wurde:
+
[source, cli]
----
cluster peer show
----
+
Das folgende Beispiel zeigt die erwartete Ausgabe für erfolgreich verbundene Cluster.

+
[listing]
----
cluster1::> cluster peer show

Peer Cluster Name   Cluster Serial Number   Availability   Authentication
-----------------   ---------------------   -------------- --------------
cluster2             1-80-123456             Available      ok
----


.Ergebnis
Die ASA und ASA r2-Cluster sind per Peering verbunden, sodass Speicher-VM-Daten sicher übertragen werden können.

.Was kommt als Nächstes?
Sie sind bereit, die Vorabprüfung der Migration auszuführen.



[[step-3-execute-the-migration-pre-check]]
== Schritt 3: Ausführen der Migrationsvorprüfung

Bevor Sie eine Storage VM von einem ASA-Cluster zu einem ASA r2-Cluster migrieren, müssen Sie einen Migrations-Pre-Check durchführen und alle erforderlichen Probleme beheben. Die Migration kann erst nach erfolgreichem Abschluss des Pre-Checks erfolgen.

.Über diese Aufgabe
Der ASA Cluster ist der Quell-Cluster, von dem die Storage VM migriert wird, und der ASA r2 Cluster ist der Ziel-Cluster, zu dem die Storage VM migriert wird.

.Schritt
. Vom Ziel-Cluster aus erfolgt die Migrationsvorprüfung:
+
[source, cli]
----
vserver migrate start -vserver <storage_VM> -source-cluster <sourcecluster> -check-only true
----
+
Wenn zur Vorbereitung auf die Migration Probleme behoben werden müssen, werden das Problem und die Korrekturmaßnahme angezeigt. Nach der Behebung des Problems ist die Vorabprüfung so lange zu wiederholen, bis sie erfolgreich abgeschlossen ist.



.Was kommt als Nächstes?
Sie sind nun bereit, Ihre Storage-VM von Ihrem ASA Cluster zu einem ASA r2-Cluster zu migrieren.



[[step-4-migrate-an-asa-storage-vm-to-an-asa-r2-cluster]]
== Schritt 4: Migrieren einer ASA -Speicher-VM zu einem ASA r2-Cluster

Nachdem Sie Ihren ASA Cluster vorbereitet und die notwendige Cluster-Peer-Beziehung mit dem ASA r2-Cluster hergestellt haben, können Sie mit der Migration der Storage-VMs beginnen.

Bei der Migration von Speicher-VMs empfiehlt es sich, sowohl auf dem ASA -Cluster als auch auf dem ASA r2-Cluster 30 % CPU-Reserve einzuplanen, damit die CPU-Workload ausgeführt werden kann.

.Über diese Aufgabe
* Nach der Migration der Storage VM gehen die Client-E/A nahtlos und ohne Unterbrechung auf den Ziel-Cluster über, und die Storage VM auf dem ASA r2 Cluster wird automatisch entfernt. Die automatische Umschaltung und die automatische Entfernung der Storage VM sind standardmäßig aktiviert. Sie können optional eine oder beide Optionen deaktivieren und manuell ausführen.
* Der ASA Cluster ist der Quell-Cluster, von dem die Storage VM migriert wird, und der ASA r2 Cluster ist der Ziel-Cluster, zu dem die Storage VM migriert wird.


.Bevor Sie beginnen
* Der ASA r2-Cluster muss über ausreichend freien Speicherplatz verfügen, um die migrierte Speicher-VM aufzunehmen.
* Wenn die ASA -Speicher-VM verschlüsselte Volumes enthält, muss der Onboard-Key-Manager oder der externe Key-Manager auf dem ASA r2-System auf Clusterebene konfiguriert werden.
* Die folgenden Operationen können auf dem Quell- ASA Cluster nicht ausgeführt werden:
+
** Failover-Operationen
** WAFLIRON
** Fingerabdruck
** Volumen verschieben, neu hosten, klonen, erstellen, konvertieren oder Analysen




.Schritte
. Der Start der Storage VM Migration erfolgt vom Ziel-Cluster aus:
+
[source, cli]
----
vserver migrate start -vserver <storage_VM_name> -source-cluster <source_cluster>
----
+
Zum Deaktivieren der automatischen Umstellung dient der  `-auto-cutover false` Parameter. Zum Deaktivieren der automatischen Entfernung der Quell-Storage-VM dient der  `-auto-source-cleanup false` Parameter.

. Überwachen Sie den Status der Migration
+
[source, cli]
----
vserver migrate show -vserver <storage_VM_name>
----
+
Falls Sie die Migration vor dem automatischen Umstieg pausieren oder abbrechen müssen, verwenden Sie die `vserver migrate pause` und die `vserver migrate abort` Befehle.  Sie müssen die Migration pausieren, bevor Sie sie abbrechen können.  Die Migration kann nach dem Start der Umstellung nicht mehr abgebrochen werden.

+
Wenn die automatische Umstellung aktiviert ist, wird nach Abschluss der Migration der *status* als *migration-complete* angezeigt. Wenn die automatische Umstellung deaktiviert ist, wird der *status* als *Ready for source cleanup* angezeigt.



.Ergebnis
Die Speicher-VM wird vom ASA Cluster zum ASA r2-Cluster migriert.  Der Name und die UUID der Speicher-VM, der Daten-LIF-Name, die IP-Adresse und Objektnamen, wie z. B. der Volumenname, bleiben unverändert.  Die UUIDs der migrierten Objekte in der Speicher-VM werden aktualisiert.

.Was kommt als Nächstes?
Wenn Sie die automatische Umstellung und die automatische Entfernung der Storage VM deaktiviert haben, umfasst die Nachmigration eine manuelle Umstellung und Bereinigung, bei der Ihre ASA Clients manuell auf Ihren Ziel-Cluster umgestellt und die Storage VM aus dem ASA Cluster entfernt wird.



[[step-5-post-migration-cutover-and-cleanup]]
== Schritt 5: Umstellung und Bereinigung nach der Migration

Bei einer clusterübergreifenden Migration einer Storage VM wird die Client-E/A auf den Ziel-Cluster umgestellt, und die Storage VM auf dem Quell-Cluster wird automatisch entfernt. Wenn Sie während der Migration die automatische Umstellung und Entfernung der Quell-Storage VM deaktivieren, müssen Sie diese Schritte manuell durchführen, nachdem der Migrationsstatus *Ready for source cleanup* erreicht wurde.



[[manually-cut-over-clients-after-a-storage-vm-migration]]
=== Manuelle Umstellung der Clients nach einer Migration einer Storage VM

Wenn Sie die automatische Client-Umschaltung während der Migration einer Storage VM zwischen Clustern deaktivieren, ist nach dem Bereitstehen der Migrationsbeziehung für die Umschaltung eine manuelle Umschaltung erforderlich, damit die Storage VM am Ziel Daten für Clients bereitstellen kann.

.Über diese Aufgabe
Die Durchführung dieser Aufgabe erfolgt vom Ziel-Cluster aus.

.Schritte
. Manuelle Clientumstellung:
+
[source, cli]
----
vserver migrate cutover -vserver <storage_VM_name>
----
. Vergewissern Sie sich, dass der Umstellungsvorgang abgeschlossen ist:
+
[source, cli]
----
vserver migrate show
----


.Ergebnis
Die Daten werden Ihren Clients von der Storage VM auf Ihrem Ziel-Cluster bereitgestellt.

.Was kommt als Nächstes?
Sie können die Storage VM nun aus dem Quell-Cluster entfernen.



[[manually-remove-a-storage-vm-after-migration]]
=== Manuelles Entfernen einer Storage VM nach der Migration

Wenn Sie die automatische Quellbereinigung während einer Migration einer Storage VM zwischen Clustern deaktivieren, sollten Sie nach Abschluss der Migration die Storage VM aus dem Quell-Cluster entfernen, um den Storage Platz freizugeben.

.Bevor Sie beginnen
Ihre Clients sollten Daten vom Ziel-Cluster bereitstellen.

.Schritte
. Im Quell-Cluster ist zu prüfen, ob der Status der Quell-Storage VM *Ready for source cleanup* lautet:
+
[source, cli]
----
vserver migrate show
----
. Entfernen der Quell-Storage VM:
+
[source, cli]
----
vserver migrate source-cleanup -vserver <storage_VM_name>
----


.Ergebnis
Die Storage VM in Ihrem Quell-Cluster wurde entfernt.
